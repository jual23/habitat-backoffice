# Phase 0 Research: Module Navigation Performance

No `NEEDS CLARIFICATION` markers remain in the Technical Context. This research is grounded in a direct audit of the current codebase (not generic best practices) — each finding below cites the file(s) that demonstrate it.

## 1. Root-cause diagnosis (why it's 2+ seconds today)

- **Decision**: Treat this as four compounding, independently-fixable causes rather than one bug:
  1. **Redundant auth/role lookups per navigation.** `getUserContext()` (`lib/session.ts`) does 2–3 sequential Supabase round trips (`auth.getUser()` → `user_roles` query → sometimes a `profiles` query). It is called once in the shared `(backoffice)/layout.tsx` *and independently again* in every module's `page.tsx` — confirmed at **38 call sites** under `app/(backoffice)/`. Since App Router layouts are not re-executed on sibling navigation, the layout's call only runs once per session, but every module switch still pays the full cost again inside that module's own `page.tsx`.
  2. **Session refresh in middleware.** `middleware.ts` runs `updateSession()` (`lib/supabase/middleware.ts`) on almost every request (its matcher excludes only static assets), which itself talks to Supabase to refresh the auth cookie — a third layer of auth-related latency on top of (1), on every navigation.
  3. **Serial (non-parallel) data queries within a module.** At least `facilities/page.tsx` fetches facilities, *then* resolves every facility's signed image URL, *then* fetches the building's timezone as a fourth, separate round trip — when the facilities query and the timezone query have no dependency on each other and could run concurrently. `finance/page.tsx`, by contrast, already parallelizes its three queries via `Promise.all` — so the codebase is inconsistent, not uniformly bad.
  4. **No loading UI anywhere.** Zero `loading.tsx` files and zero uses of `<Suspense>`/`next/dynamic` exist anywhere under `app/`. Without a route-segment `loading.tsx`, Next.js's App Router keeps the *previous* page fully visible and unresponsive-looking until the entire destination `page.tsx` (all of the above, serially) resolves — this is why the wait reads as "did it freeze?" rather than "it's loading."
- **Rationale**: Each cause is independently verifiable in the code (not speculative) and independently fixable without touching the others, which lets the fix be delivered incrementally and matches Principle V (smallest change that addresses the measured problem).
- **Alternatives considered**: Reaching for a broad rewrite (e.g., moving data-fetching to a client-side cache layer/SWR-style library) — rejected as disproportionate; every cause above has a fix already native to the framework/stack in use.

## 2. De-duplicating `getUserContext()` per request

- **Decision (revised during implementation — see below)**: Keep `getUserContext(supabase)`'s existing signature **unchanged**. Wrap `createClient()` (`lib/supabase/server.ts`) in a per-request cache so every caller within one request receives the *same* Supabase client instance, and wrap `getUserContext()` in the same mechanism, keyed on that now-stable `supabase` argument. Both use a small local helper, `requestCache()` (`lib/request-cache.ts`), rather than importing React's `cache()` directly — see §2b for why.
- **Why the client itself must be cached, not just the auth lookup**: `createClient()` takes no arguments and previously returned a **new** Supabase client instance on every call — `layout.tsx` and each module's `page.tsx` each called it independently. A memoized function keyed by argument identity (which is how React's `cache()` — and `requestCache()`, when it delegates to `cache()` — behaves) needs the *same* object passed in on every call to actually hit; two different client instances would look like two different calls and never dedupe. So `createClient()` is cached first, and `getUserContext(supabase)` is cached second, reading from the now-request-stable client every caller shares.
- **Revision — why `getUserContext()` keeps its parameter instead of self-fetching a client**: The original plan for this section called for `getUserContext()` to drop its `supabase` parameter and call `createClient()` internally. That was reverted during implementation (T002/T003) once writing the Constitution Principle III test (`tests/integration/get-user-context.test.ts`) surfaced the real constraint: `createClient()` calls `next/headers`'s `cookies()`, which throws outside a live Next.js request context — exactly the environment Vitest runs tests in. `lib/user-provisioning.ts`'s `createBuildingUser()` already established the pattern this codebase uses for exactly this reason (see its own doc comment): authorization-relevant functions take their Supabase client as a plain argument specifically so they can be exercised directly in an integration test, the same way a real request would call them, without needing to fake a Next.js request context. `getUserContext()` follows that same established convention.
- **Rationale**: This still fully solves the original problem (`getUserContext()`'s `auth.getUser()`/`user_roles`/`profiles` round trips no longer repeat once per caller within a request) while keeping the function testable and consistent with how this codebase already tests its other authorization-relevant functions. It ships with React/Next.js already (no new dependency, Principle V), and — critically for Principle I — the cache is scoped to a single request and is never shared across requests or users, so there is no cross-tenant leakage risk from adopting it.
- **Constitution gate (Principle III, NON-NEGOTIABLE)**: Because this changes how an authorization-determining function is invoked, tests MUST assert the memoized `getUserContext()` returns identical results to today's implementation for every `UserContext` shape (app_admin, building_admin, staff, resident, renter, no-role/null, signed-out) before or alongside the change — not as an afterthought. `tests/integration/get-user-context.test.ts` does this directly against the live project's RLS, following `tests/integration/user-provisioning.test.ts`'s established style.
- **Alternatives considered**:
  - *Drop the `supabase` parameter, have `getUserContext()` call `createClient()` internally* — reverted (see revision above): it breaks direct testability, the established pattern in this codebase for authorization-relevant functions.
  - *Passing context down as props from layout to page* — rejected; Next.js App Router layouts and pages for sibling routes aren't structured for straightforward prop-drilling of server-computed data across that boundary without extra plumbing that a per-request cache avoids entirely.
  - *`unstable_cache` / Next.js Data Cache* — rejected specifically for auth/role data: that cache is designed to persist *across* requests (with revalidation), which is the wrong lifetime for something as sensitive as "which building can this user see" — Principle I requires this to reset every request.

## 2b. `requestCache()` instead of importing React's `cache()` directly

- **Decision**: Both `createClient()` and `getUserContext()` are wrapped via a small local helper, `requestCache()` (`lib/request-cache.ts`), instead of `import { cache } from 'react'` directly. `requestCache()` uses `React.cache` when it's present on the resolved `react` build, and silently falls back to the plain, unwrapped function otherwise.
- **Why**: `cache()` is only exported by the special React build Next.js's own bundler substitutes in for Server Components. The plain `react` package installed in `node_modules` — what Vitest resolves when a test file imports a module using this — does not export `cache` at all. Discovered directly while running `tests/integration/get-user-context.test.ts`: importing `lib/session.ts` crashed at module-load time with `TypeError: cache is not a function` the moment the test file (not Next.js's bundler) resolved `react`. `requestCache()` fixes this without sacrificing either goal: real per-request memoization inside the actual Next.js app (where `React.cache` is present), and full callability inside Vitest (where it silently becomes a no-op passthrough — no caching, but no crash, and no wrong test results, since a fresh, correct computation is exactly what each test call gets).
- **Rationale**: This is a minimal, well-scoped shim — one function, no new dependency — rather than reaching for a testing-library-specific mock/alias configuration in `vitest.config.ts`, which would be more moving parts for the same outcome (Principle V).
- **Alternatives considered**:
  - *Configure Vitest to alias `react` to a build that exports `cache`* — rejected: more configuration surface, and would apply globally to every test file rather than being scoped to the two call sites that actually need it.
  - *Mock `react`'s `cache` export in test setup* — rejected: same downside, plus every future test author would need to know this mock exists and why.

## 3. Middleware session refresh

- **Decision**: Leave `middleware.ts`'s `updateSession()` call as-is for this feature — it is the Supabase-recommended pattern for refreshing the auth cookie and is a separate concern (cookie freshness) from the redundant *role/building* lookups being fixed in §2.
- **Rationale**: Removing or restructuring session-cookie refresh is a higher-risk change to the authentication boundary itself, with a much smaller payoff than fixing the 38-call-site duplication — not justified by this feature's scope (spec Assumptions: "does not alter existing authorization rules").
- **Alternatives considered**: Skipping middleware on backoffice routes entirely — rejected outright, this is precisely the mechanism keeping sessions valid and is out of scope to weaken.

## 4. Parallelizing per-module queries

- **Decision**: Audit each module's `page.tsx` individually (tracked per-module in tasks.md) and convert any sequential `await` chain of *independent* Supabase queries into a single `Promise.all`, following the pattern `finance/page.tsx` already uses. Where a later query genuinely depends on an earlier one's result (e.g., using an ID returned by the first query), the dependency is preserved — only independent work is parallelized.
- **Rationale**: This directly removes the serial round trips identified in §1.3, with a pattern already proven correct and in use elsewhere in the same codebase (no new pattern to learn or review).
- **Alternatives considered**: A generic "data loader"/batching abstraction — rejected under Principle V as unnecessary; `Promise.all` over a handful of independent Supabase calls per module is already the simplest fix and matches existing code style.

## 5. Signed-URL regeneration on every visit

- **Decision**: For this version, do not introduce a new caching layer (in-memory, KV, or otherwise) for Storage signed URLs; instead ensure signed-URL generation for a given module is itself parallelized (§4) rather than serialized with other queries, and revisit dedicated caching only if measurement (quickstart.md) shows image-heavy modules (Facilities, Activities, Announcements) still miss the target after §2 and §4 land.
- **Rationale**: `trySignedUrlFor()` (`lib/supabase/storage.ts`) makes a real Storage API round trip per image, regenerated on every page visit even though a previously-issued URL may still be valid for up to 24h — but building a correctly-scoped cache (keyed per exact `{bucket, path}`, with a TTL safely shorter than the signed URL's own expiry, per Principle I) is real added complexity. Principle V favors first landing the two clearly-justified, low-risk fixes (§2, §4) and re-measuring before adding a caching layer whose benefit is currently unproven for most modules (only image-heavy ones would benefit meaningfully).
- **Alternatives considered**:
  - *Switch facility/announcement/activity images to a public bucket + `next/image`* — rejected, this would undo the private-Storage/RLS-gated design deliberately chosen in `003-upload-display-fix` (Principle I concern) and is out of scope for a navigation-speed fix.
  - *Add an in-memory signed-URL cache now* — deferred, not rejected: captured here as the documented next step if post-fix measurement still shows a gap (see quickstart.md).

## 6. Instant loading feedback via `loading.tsx`

- **Decision**: Add a `loading.tsx` file next to every module's `page.tsx` (18 modules — the 17 in `sidebar-nav.tsx` plus Reservations, which has its own page but isn't a sidebar link), rendering a lightweight skeleton that matches the module's general layout (e.g., a list-shaped skeleton for list-style modules). This is Next.js's native App Router convention: React automatically wraps `page.tsx` in a `<Suspense>` boundary using the sibling `loading.tsx` as its fallback.
- **Rationale**: This is the direct, framework-native fix for FR-003/SC-004 ("a loading indicator appears within 300ms so the screen never looks frozen") and requires no new library, no manual `<Suspense>` wiring, and composes automatically with the shared `layout.tsx` (which keeps rendering — sidebar and header stay interactive while only the `main` content area shows the loading state).
- **Alternatives considered**: A hand-rolled global loading spinner triggered from client-side route-change events — rejected; it would require a second navigation-tracking mechanism layered on top of the framework's own router, which is exactly the kind of competing complexity the Client Platform Requirements section already warns against for routing.

## 7. Measuring "loading time" for validation

- **Decision**: Measure navigation time as wall-clock time from a `next/link` click to the destination module's primary content being visible, using the browser DevTools Performance/Network panel (or simple `performance.now()` console markers during manual testing) across a fixed, representative set of module-to-module transitions — not a synthetic/automated benchmark suite for this version.
- **Rationale**: Matches the spec's own Assumptions (click-to-visible-content, typical broadband, warm session) and is the simplest way to verify SC-001–SC-004 without adding new tooling/dependencies (Principle V); a fixed transition set (see quickstart.md) makes before/after comparison repeatable across modules and roles per FR-005/SC-005.
- **Alternatives considered**: Standing up an automated performance-testing pipeline (e.g., Lighthouse CI in CI/CD) — deferred as disproportionate for validating this single fix; worth considering separately if navigation performance work becomes ongoing.

## 8. Scope boundary: what this feature does *not* change

- **Decision**: This feature does not alter what any module displays, what data it queries, or who can access it (spec Assumptions) — every change is either (a) computing already-correct data fewer times per request, (b) reordering already-independent queries to run concurrently, (c) capping how much of a large list is fetched at once (§9), or (d) adding a loading state that didn't exist before. No query's filter/`.eq()` conditions, no RLS policy, and no role-check logic changes — §9's `LIMIT`/`range()` narrows *how many rows* a list query returns, not *which* rows a user is authorized to see.
- **Rationale**: Keeps the Constitution Check's PASS verdicts valid — this is a behavior-preserving performance refactor, not a functional change, and Principle III's testing gate exists precisely to prove that.

## 9. Bounding large module data sets (batch-limiting, with optional pagination)

- **Decision**: Every module's primary list query fetches only an initial batch of ~25 records (e.g., `.range(0, 24)` or `.limit(25)`, ordered consistently so the batch is stable) instead of the full table, for any module whose content is naturally a list that can grow large (Facilities, Incidencias, Packages, Announcements, Activities, Visitors, Apartments, Users, Polls, Suggestions/Complaints, Broadcast, Maintenance, Emergency, Reservations, Finance's payments list). Where a module's UI reasonably supports it, a simple "load more"/pagination control lets the user fetch the next batch on demand — this is a per-module SHOULD, not a MUST, since some modules' content may not need it (e.g., a small fixed set of settings).
- **Rationale**: This directly implements FR-008 and reinforces the whole feature's goal: a smaller initial payload is faster to fetch, faster to serialize, and faster to render, on top of (not instead of) the `getUserContext()` dedup (§2) and query parallelization (§4) — all three compound. It also sidesteps the harder problem of true in-page streaming (nested `<Suspense>` around a slow subtree): capping the query itself is simpler (Principle V) and solves the same underlying problem (a large data set delaying the whole page) for the common case of "a list has grown large," which is what actually causes slow navigations in this app today, rather than genuinely un-chunkable content.
- **Alternatives considered**:
  - *Fetch everything, then virtualize/paginate client-side* — rejected: the network fetch and server-side serialization of the full data set is exactly the cost this feature is trying to remove; virtualizing after the fact doesn't help time-to-first-content.
  - *Nested `<Suspense>` streaming within a page for the "remaining data"* — deferred, not rejected outright: more powerful (true progressive rendering of a single large fetch) but meaningfully more complex to introduce correctly across 18 modules than a query `LIMIT`; revisit only if a specific module's content genuinely can't be usefully batched (none identified so far).
  - *A different fixed batch size (e.g., 10, 50, 100)* — 25 is the figure specified for this feature; spec.md's Assumptions note it as a starting default a module may reasonably deviate from, not a hard universal constant.
