# Phase 0 Research: App Administrator Building Management

No `NEEDS CLARIFICATION` markers remain in the Technical Context. This research is grounded in a direct audit of the current codebase — each finding cites the file(s) that demonstrate it.

## 1. Why App Administrator's navigation shows modules that don't actually work for them today

- **Finding**: `app/(backoffice)/sidebar-nav.tsx`'s `SidebarNav` filters `NAV_ITEMS` only by `staffOnly` — there is no equivalent filter for `app_admin`. Every module's `page.tsx` allows the role check `ctx.role !== 'building_admin' && ctx.role !== 'app_admin'` to pass for App Administrator, but then does `const buildingId = ctx.buildingId; if (!buildingId) return <p>...manage this per-building elsewhere.</p>;` — and `getUserContext()` (`lib/session.ts`) always returns `buildingId: null` for `app_admin`. So today, App Administrator sees a full navigation but every link (including Users, confirmed by reading `users/page.tsx`) leads to that same placeholder — there is no "elsewhere" it refers to.
- **Decision**: Fix this at two levels — hide the links that will never work for this role (FR-001, §2 below), and make the one link that's supposed to work (Users) actually work by giving it role-appropriate content (FR-003, §3 below) instead of leaving it to hit the same placeholder.

## 2. Restricting App Administrator's navigation

- **Decision**: Extend `layout.tsx`'s existing pattern (`isStaffOnly = ctx.role === 'staff'`, passed to `SidebarNav`) with `isAppAdmin = ctx.role === 'app_admin'`, and extend `SidebarNav`'s filter: when `isAppAdmin`, `items = NAV_ITEMS.filter((item) => item.href === '/users')`.
- **Rationale**: This is the exact mechanism already used for Staff's narrower nav — no new pattern, no new component, matches Principle V.
- **Alternatives considered**: A separate `NAV_ITEMS_APP_ADMIN` array — rejected, more to keep in sync for no benefit over a one-line filter given the target is a single item.

## 3. Users module content, branched by role

- **Decision**: `app/(backoffice)/users/page.tsx` branches near the top, right after resolving `ctx`: if `ctx.role === 'app_admin'`, fetch buildings + their current administrators and render a new `BuildingsClient`; otherwise (today's `building_admin` path), proceed exactly as today, unchanged, rendering the existing `UsersClient`.
- **Rationale**: Keeps Building Administrator's code path — `users-client.tsx`, `actions.ts`, every query in the `building_admin` branch — completely untouched (FR-002/SC-005), while giving App Administrator real, working content at the one link they keep (FR-003).
- **Alternatives considered**: A single combined component handling both roles' UI — rejected, the two audiences' data and actions don't overlap at all (buildings/administrators vs. residents/staff/invitations); combining them would only add conditional complexity with no shared logic to justify it (Principle V).

## 4. Extending `createBuildingUser()` for `building_admin`

- **Decision**: Widen `lib/user-provisioning.ts`'s `createBuildingUser()` role union from `'resident' | 'renter' | 'staff'` to also include `'building_admin'`, following the exact shape Staff already uses (no `apartmentId`, a plain `user_roles` insert with `role: 'building_admin', building_id: buildingId`).
- **Rationale**: This function already handles the two things a new Building Administrator account needs — an Admin-API `auth.users` row with an admin-set password (`adminClient.auth.admin.createUser()`) and a scoped `user_roles` row — via the same code path Staff already uses, just a different `role` value in the insert. Reuses the function's existing rollback-on-failure behavior (if the `user_roles` insert fails, the just-created `auth.users` row is deleted) unchanged.
- **Alternatives considered**: A separate `createBuildingAdministrator()` function duplicating most of `createBuildingUser()`'s body — rejected as unnecessary duplication for a one-branch difference (Principle V).

## 5. No changes needed to the other 16 modules' `page.tsx` files

- **Decision**: Do not touch `facilities/page.tsx`, `finance/page.tsx`, or any of the other building-operational modules' access checks. Their existing `if (!ctx.buildingId) return <p>...manage this per-building elsewhere.</p>;` fallback already satisfies spec.md's own Acceptance Scenario (User Story 1, Scenario 3): "they see the same 'not available for this role' fallback that already exists today."
- **Rationale**: Since the navigation no longer links to these pages for App Administrator (§2), the only way to reach one is typing its URL directly — and that already degrades gracefully today, with no data ever shown, because `buildingId` is null. Changing 16 files' role checks to explicitly exclude `app_admin` would be a larger, higher-risk surface for a purely cosmetic improvement over the current, already-safe fallback. Principle V favors the smaller change; revisit only if a future spec asks for that placeholder itself to change.
- **Alternatives considered**: Removing `app_admin` from all 16 modules' role checks so they 403/redirect instead of rendering a placeholder — deferred, not rejected outright; tracked as a possible follow-up, not required by this spec's acceptance criteria.

## 6. RLS policy verification for the new writes

- **Decision**: Before implementing the new Server Actions, verify against the live Supabase project whether App Administrator already has:
  1. `buildings`: INSERT and UPDATE permission (needed for FR-005/FR-007).
  2. `user_roles`: INSERT and DELETE permission for rows where `role = 'building_admin'` (needed for FR-006/FR-009).
  3. `buildings`: SELECT-all (no `building_id` filter) permission (needed for FR-004) — very likely already present, since Principle I already treats "App Administrator spans all buildings" as foundational and several existing RLS policies (tickets, payments, maintenance, emergencies, broadcasts — confirmed via `supabase/migrations/*_rls.sql` comments) already branch on `is_app_admin` for broad access; this one is the lowest-risk of the three to assume, but is still verified before relying on it.
  If any of these are missing, add them via one additive migration, following the exact pattern `specs/001-building-backoffice/SCHEMA-ADAPTATION.md` already documents for this project (e.g., its `user_roles_staff_provisioning_policies` migration, which added the analogous INSERT/DELETE policies letting a `building_admin` provision/remove `staff` rows scoped to their own building).
- **Rationale**: The live schema predates this codebase and was not built from this repo's own migration history (SCHEMA-ADAPTATION.md) — assuming a policy's presence without checking has already caused documented gaps in this project before (e.g., the `invitations_role_scoping_policies` migration fixed a privilege-escalation gap found this same way). Checking first, and adding only what's missing, keeps this feature from either failing silently at runtime or opening more access than intended.
- **Alternatives considered**: Routing the `buildings` INSERT/UPDATE through the service-role admin client (`getAdminClient()`) to sidestep RLS entirely — rejected: the admin client is reserved, by existing convention and the constitution's Security section, for the one thing regular RLS-enforced clients categorically cannot do (creating `auth.users` rows with admin-set passwords); a `buildings` row is ordinary application data with no such limitation and belongs behind a proper RLS policy like every other table in this app, not a service-role bypass.

## 7. `requireBuildingAdmin()` in `users/actions.ts` is left unchanged

- **Decision**: Do not modify `requireBuildingAdmin()` (which currently allows both `building_admin` and `app_admin`) or the resident/staff actions it guards (`createResident`, `updateResident`, `deleteResident`, `cancelResidentInvitation`).
- **Rationale**: Per §3/§5, App Administrator's Users-module UI never calls these actions — their own new UI (`buildings-client.tsx`) calls the new `buildings-actions.ts` functions instead, which independently require `ctx.role === 'app_admin'`. Since App Administrator's `ctx.buildingId` is always `null`, every one of `requireBuildingAdmin()`'s existing callers already fails their own `if (!ctx.buildingId) return { ok: false, ... }` check today if somehow invoked by App Administrator (confirmed in `createResident`, for example) — so there is no real access-control gap to close here, only a redundant allowance that costs nothing to leave as-is (Principle V: don't touch working, unrelated code without a concrete reason).
- **Alternatives considered**: Removing `app_admin` from `requireBuildingAdmin()`'s allowed roles for tighter defense-in-depth — deferred as an optional hardening step, not required (see §5's reasoning); could be picked up in the same follow-up as §5's alternative if desired later.

## 8. Ordering writes so a building is never left without an administrator (FR-011)

- **Decision**:
  - **Creation, new-account path**: (1) insert the `buildings` row (name only — logo and administrator come after, buildings' other columns already have defaults per the live schema); (2) if a logo was provided, upload it and update `logo_url` (best-effort — a failure here does not roll back the building, since logo is optional per FR-005); (3) create the Building Administrator account via the extended `createBuildingUser()` (§4). **If step 3 fails, delete the building row created in step 1** — mirroring `createBuildingUser()`'s own existing "roll back the just-created auth account if the role insert fails" pattern, so a failed creation never leaves an administrator-less building behind.
  - **Creation, existing-administrator path** (§10): steps (1)–(2) are identical; step (3) is a plain `user_roles` insert (`{ user_id: <selected existing Building Administrator>, role: 'building_admin', building_id: <new building's id> }`) instead of `createBuildingUser()` — no new `auth.users` row is created at all. **If this insert fails, delete the building row created in step 1**, same rollback reasoning.
  - **Reassignment** (including assigning an administrator to a building that currently has none, FR-011): insert the **new** `user_roles` row for the incoming Building Administrator **before** deleting the outgoing one's row, if one exists (deleting zero rows is a harmless no-op for the "currently has none" case). This means there is, at most, a brief moment with two `building_admin` rows for the same building rather than a moment with zero — the safer direction to fail toward, since Supabase's JS client has no simple multi-statement transaction primitive available to application code (unlike a single RPC call).
- **Rationale**: FR-011 ("MUST NOT allow a building to exist without exactly one designated Building Administrator") and the spec's edge case ("a failed reassignment must not leave a building without an administrator") both require this ordering discipline specifically, not just "do the two writes."
- **Alternatives considered**: A single SQL function (RPC, `SECURITY DEFINER`) performing the whole create-or-reassign atomically — more robust in principle, but a larger, riskier change (a new database function alongside new RLS policies) for a feature whose failure window is already narrow and whose failure mode (delete-the-orphaned-building / two-admins-briefly) is acceptable and cheap to reason about; revisit only if this ordering proves insufficient in practice (Principle V).

## 9. Building creation/edit fields

- **Decision**: The building create/edit form has exactly two fields: `name` (required) and `logo` (optional), reusing Customization's own logo-upload mechanics (`uploadBuildingFile()`, `STORAGE_BUCKETS.media`, the same square-image validation `updateCustomization()` already performs). `accent_color` and every other `buildings` column keep their existing database defaults and are left for the new Building Administrator to change via Customization themselves, exactly as happens for a building today.
- **Rationale**: Matches the feature description precisely ("give them a name and logo, the same fields that go into the customization tab, but from a creation perspective") and spec.md's Assumptions, which explicitly scope the form to these two fields.
- **Alternatives considered**: Also exposing `accent_color` at creation — rejected as unrequested scope; easy to add later without any structural change if asked for.

**New-administrator-account form fields**: `lib/validation/buildings.ts`'s schema for the new-account path (email, password, first name, last name, document ID) duplicates `lib/validation/users.ts`'s existing `baseAccountFields` shape rather than importing it — `baseAccountFields` is a module-private `const` there (not `export`ed), and adding an export to `users.ts` (a Building-Administrator-facing file) solely for this feature would cut against §3/§7's "never touch Building-Administrator-facing files" decision for a five-field object with no behavior to keep in sync. If the two shapes ever need to diverge, they already can with zero coordination cost.

## 10. Selecting an existing Building Administrator (dropdown), instead of always creating a new account

- **Decision**: Both the create-building flow (FR-006) and the reassign flow (FR-009) offer the App Administrator a choice: create a brand-new Building Administrator account (§4/§8's new-account path), or select an existing one from a dropdown. That dropdown is populated from a single query — all `user_roles` rows where `role = 'building_admin'`, joined to each user's display profile — deduplicated by user, since the same person may already administer more than one building (spec.md Assumptions). **App Administrator accounts are never included in this dropdown, even though they are also, technically, an administrative role** (FR-013).
- **Why App Administrator is excluded — not just a scope choice, a functional one**: `getUserContext()` (`lib/session.ts`) resolves a signed-in user's role by checking for an `app_admin` `user_roles` row *first*, and returns immediately if one is found — a user who held both an `app_admin` row and a `building_admin` row would always resolve as `app_admin` (`buildingId: null`) and could never actually exercise the Building Administrator access such an assignment would nominally grant them. Assigning an App Administrator as a building's administrator would silently create an unusable assignment — worse than not offering it. This feature does not change that role-resolution precedence (out of scope — changing it would affect every existing module's authorization check, not just this one).
- **This directly resolves the coverage gap `/speckit-analyze` flagged around SC-003** (a building that predates this feature might already lack a Building Administrator): the same dropdown-or-create-new choice used for reassignment is exactly the single self-service action FR-011's updated wording promises for fixing one — no separate "adopt an orphaned building" flow or function is needed; `reassignBuildingAdministrator()` (§8, "Reassignment") already handles a building with zero existing administrators as a special case of its normal delete-the-outgoing-row step being a no-op.
- **Alternatives considered**:
  - *A dropdown of all existing users, any role* — rejected: the point is reusing someone who has already been vetted and onboarded as a Building Administrator specifically; promoting an arbitrary Resident or Staff account to Building Administrator directly, with no account-creation step, wasn't asked for and skips the "administrator-appropriate account details" (first/last name, document ID) this flow otherwise collects.
  - *Including App Administrator accounts in the dropdown* — rejected for the functional reason above, not merely a preference.
